# 제16장. 확장 부스터: 서드브레인 아키텍처 구축

> "도메인마다 따로 세우지 않는다. 한 플랫폼 + 세 부스터." — 오픈브레인 시스템 제안서 (이형근, 2026)

몇 해 전, 연 매출 200억 원 규모의 한 전자부품 제조사를 진단하러 갔을 때의 일이다. 서버실 랙에는 시스템이 다섯 개 들어 있었다. 국산 ERP, 외산 MES, 스케줄링 전용 APS, BI 대시보드, 그리고 그 사이를 잇는다는 명목으로 개발된 정체불명의 '인터페이스 서버'. 각 시스템은 도입 당시의 제안서 속에서는 모두 옳았다. 그러나 다섯 개의 시스템은 다섯 개의 품목 마스터를 낳았고, 매주 월요일 아침 생산관리 담당자는 네 시간 동안 엑셀로 시스템 간 수치를 '맞추는' 일을 하고 있었다. 통합을 위해 도입한 시스템들이 통합을 가장 어렵게 만드는 역설 — 나는 이것을 '시스템의 군도(群島)'라 부른다. 섬은 많은데 다리가 없고, 다리를 놓을 때마다 유지보수비가 자란다. 이 장은 그 군도의 반대편 설계를 다룬다. 하나의 대륙(단일 플랫폼) 위에 세 개의 타워(부스터)를 세우는 것, 그리고 그 타워들이 1부 5장에서 설계한 LLM 무한 루프의 부품으로 맞물려 돌아가게 만드는 것이다.

15장의 결론은 명확했다. Odoo에 내장된 AI는 기록 위의 지능으로서 훌륭한 출발점이지만, 세 가지가 부족하다. 유한능력의 정밀한 계획 능력, 시스템 경계를 넘는 자동화의 배관, 그리고 기업의 의미 구조를 이해하는 온톨로지 기억이다. 이 장은 그 결핍을 메우는 확장 부스터 — frePPLe, n8n과 Dify, Neo4j GraphRAG, 그리고 Ollama/Claude의 LLM 이중화 — 를 '기능 소개'가 아니라 '구축 컨설팅'의 관점에서 다룬다. 어떤 성숙도에서 어떤 부스터를 어떤 순서로 도입하고, 보안과 비용은 어떻게 설계하며, 무엇이 어렵고 무엇을 각오해야 하는가. 1부 7장에서 그린 예측 플랫폼 아키텍처의 실장(實裝) 매뉴얼이 이 장의 정체다.

## 16.1 왜 부스터인가: 병립의 함정과 원플랫폼+쓰리부스터

전통적 확장 경로는 도메인별 전문 시스템의 병립이었다. 계획이 어려우면 APS를 사고, 현장이 안 보이면 MES를 사고, 보고서가 부족하면 BI를 산다. 각 도구는 해당 도메인에서 최적이지만, 전체는 최적이 아니다. 이유는 2부 8장에서 논한 단일 플랫폼 원리의 정확한 반대가 일어나기 때문이다. 시스템마다 품목·거래처·공정의 사본이 생기고(정위치의 붕괴), 인터페이스마다 변환 규칙이 생기며(정품의 붕괴), 동기화 주기마다 시차가 생긴다(정량의 붕괴). 데이터의 3정5S를 2장에서 애써 세워 놓아도, 병립 아키텍처는 그것을 시스템 경계에서 도로 무너뜨린다. 게다가 비용 구조가 가혹하다. 중소기업이 APS·MES·BI를 각각 상용 라이선스로 도입하면 초기 비용은 억 단위로 올라가는데, 중소기업 AI 도입의 최대 장벽이 초기 비용 부담이라는 조사 결과(중소기업중앙회, 2024)를 상기하면 이 경로는 대부분의 50인 이하 기업에게 애초에 닫혀 있다.

원플랫폼+쓰리부스터(One Platform + Three Boosters)는 이 함정에 대한 아키텍처 차원의 응답이다(이형근, 2026). 원칙은 세 가지다. 첫째, 데이터의 원천은 언제나 Odoo의 단일 PostgreSQL 하나다. 부스터는 플랫폼을 대체하지 않고 보강하며, 어떤 부스터도 자기만의 마스터를 갖지 않는다. 둘째, 모든 부스터는 오픈소스이거나 소스 공개형이다. 50인 이하, 매출 50~300억 원 규모의 기업이 소프트웨어 라이선스 비용 없이, IT 전담 인력 0~1명으로 운영 가능한 표준 구성을 지향한다. 셋째, 전체를 관통하는 것은 환류 루프다. 데이터는 위로(ETL), 판단은 아래로(작업지시·마스터 개정의 환류) 흐른다.

```
┌──────────────────────────────────────────────────────────┐
│ 지식 부스터   Neo4j 온톨로지 GraphRAG + LLM(Claude/Ollama 이중화) │ ← 3rd Brain
├──────────────────────────────────────────────────────────┤
│ AX 부스터    n8n 워크플로 허브(ETL·트리거) + Dify 사내 AI 앱      │
├──────────────────────────────────────────────────────────┤
│ 계획 부스터   frePPLe APS (Odoo 공식 커넥터 — 유한능력·What-if)   │
├──────────────────────────────────────────────────────────┤
│ ONE PLATFORM  Odoo: ERP+MES+SCM — 단일 PostgreSQL          │ ← 2nd Brain
├──────────────────────────────────────────────────────────┤
│ 현장 계층     작업자(개인지식·암묵지)·설비·센서·바코드/POP        │ ← 1st Brain
└──────────────────────────────────────────────────────────┘
        환류: 데이터는 위로(ETL) │ 판단은 아래로(액션·마스터 환류)
```

이 그림은 1부 7장의 예측 플랫폼 총괄 아키텍처와 같은 구조물을 도입자의 시선으로 다시 그린 것이다. 7장이 "완성된 상태"를 보였다면, 이 장의 과제는 "어떤 순서로, 얼마의 비용으로, 어떤 위험을 관리하며" 그 상태에 도달하는가이다. 그 논의를 위해 먼저 각 부스터의 정체를 컨설턴트의 언어로 해부한다.

## 16.2 세 부스터의 해부: 계획, 자동화, 지식

### 계획 부스터 frePPLe — 유한능력의 세계로

13장에서 확인했듯 Odoo의 제조 관리는 MRP와 MPS, 간트 계획까지 지원하지만, 표준 스케줄러는 자원 능력의 제약을 정밀하게 반영하는 데 한계가 있다. 설비 8대와 작업자 12명, 자재 입고 일정이라는 유한한 제약 아래 수백 개 제조 오더의 순서를 최적화하는 문제는 전문 APS(Advanced Planning and Scheduling)의 영역이다. frePPLe는 가장 널리 쓰이는 오픈소스 APS로, 자원·인력·자재·리드타임의 제약을 모두 반영한 유한능력(finite capacity) 계획과 스케줄을 생성하고, 통계적 수요예측과 안전재고 계획, 시나리오 비교(What-if)까지 계획 업무 전반을 포괄한다(frePPLe 공식 문서). 결정적으로 Odoo 공식 커넥터가 있다. 품목·BOM·워크센터·판매 오더·재고를 frePPLe로 보내고, 계산된 제조·구매 오더 제안을 Odoo로 돌려받는다. ERP를 바꾸지 않고 계획 두뇌만 이식하는 구조이며, 오픈코어 모델이므로 소규모 제조라면 커뮤니티 에디션과 커넥터만으로 시작할 수 있다. 1부 4장의 부품전개·일정계획 방법론과 7장의 편성 시뮬레이션이 이 엔진 위에서 실행된다.

### AX 부스터 n8n과 Dify — 배관과 작업대

n8n은 페어코드(fair-code) 라이선스의 워크플로 자동화 플랫폼으로, 수백 개의 시스템 연동 노드를 시각적 캔버스에서 조립한다(n8n 공식 문서). 자체 서버에 설치할 수 있어 데이터가 외부 SaaS를 거치지 않는다는 점이 Zapier류 클라우드 자동화와의 결정적 차이다. 이 아키텍처에서 n8n의 역할은 두 가지다. ETL 파이프라인 — Odoo의 트랜잭션을 추출·변환해 Neo4j 그래프에 적재하고, 오픈마켓·택배사·센서 같은 외부 소스를 Odoo로 모은다. 그리고 워크플로 허브 — "불량 보고가 등록되면 사진을 LLM에 보내 부위를 판독하고 품질 레코드에 기록한 뒤 담당자에게 알린다" 같은 시스템 횡단 자동화를 코드 없이 구성한다. LLM·에이전트 노드가 내장되어 자동화 배관 안에 AI 판단 단계를 끼워 넣을 수 있다는 점도 중요하다.

Dify는 오픈소스 LLM 애플리케이션 개발 플랫폼이다. 프롬프트 설계, RAG 파이프라인, 에이전트 워크플로, 모델 관리와 관측(observability)을 하나의 시각적 작업대에서 제공하며 자체 호스팅할 수 있다(Dify 공식 문서). 상품 FAQ 봇, 작업표준 질의응답, CS 답변 초안 생성기 같은 업무별 사내 AI 앱을 개발자 없이 만들고 지식베이스를 연결한다. 두 도구의 역할 경계는 이렇게 정리된다. n8n은 "언제 무엇을 실행할 것인가"의 흐름 제어에, Dify는 "어떻게 답할 것인가"의 지능 구성에 강하다. 실무 표준 패턴은 n8n이 이벤트를 감지해 Dify 앱의 API를 호출하고, Dify가 RAG와 LLM으로 판단한 결과를 n8n이 Odoo 레코드에 기록하는 접속이다.

### 지식 부스터 Neo4j GraphRAG — 서드브레인의 본체

세 번째 부스터가 이 책의 핵심인 지식 계층이다. Neo4j는 대표적인 속성 그래프 데이터베이스로, 노드와 관계와 속성을 원시 자료구조로 저장하고 Cypher 질의어로 관계를 탐색한다. 이 위에 GraphRAG — LLM으로 지식그래프를 구축하고 그래프 탐색과 커뮤니티 요약으로 검색을 증강하는 기법(Edge et al., 2024) — 를 얹으면, 벡터 RAG가 놓치는 두 능력이 열린다. 여러 레코드를 가로지르는 다중 홉 질의("이 불량 로트에 들어간 자재의 공급업체가 납품한 다른 로트는?")와, 데이터 전체를 조망하는 전역 요약("올해 우리 품질 문제의 구조적 패턴은?")이다. 15장에서 진단한 Odoo AI의 결정적 한계 — 온톨로지의 부재 — 를 정확히 메우는 층이며, 1부 7장의 디지털 트윈이 서는 무대이기도 하다. 이 그래프는 검색 인덱스를 넘어 개인지식과 기업지식이 만나는 심장이다. 베테랑의 노트가 LLM 구조화와 본인 승인·익명화를 거쳐 온톨로지에 기여하고(개인→기업), 회사의 사례·통계가 개인 질의의 컨텍스트로 돌아온다(기업→개인). 공통 코드체계 — 2장에서 정비한 데이터의 정위치 — 가 두 세계의 연결 고리가 된다(이형근, 2026).

### LLM 이중화 — Ollama와 Claude, 데이터 주권과 성능의 분업

LLM 전략은 이중화다. Ollama는 Llama·Qwen 계열의 오픈소스 LLM을 자체 하드웨어(또는 전용 클라우드 GPU)에서 구동하게 하는 실행 환경으로, 프롬프트와 출력이 네트워크 밖으로 나가지 않아 데이터 주권을 확보하고 토큰당 과금을 제거한다. 반면 다단계 원인 분석, 장문 보고서, 코드 생성 같은 고난도 추론은 Claude 같은 프론티어 모델이 여전히 앞선다. 실무 설계는 과업의 민감도와 난이도의 2×2로 갈린다. 민감 데이터를 다루는 일상 과업(주문 분류, 불량 기록 구조화, 사내 문서 질의)은 자체 호스팅 소형 모델이, 민감 데이터를 익명화한 고난도 과업(경영 분석, 시나리오 해석)은 프론티어 모델이 맡는다. Dify와 n8n이 모델 추상화 계층을 제공하므로 이 라우팅은 코드 수정 없이 설정으로 운영되며, 특정 모델·특정 사업자에 대한 종속이 구조적으로 회피된다. 15장에서 지적한 Odoo AI의 범용 LLM 종속성에 대한 답이 바로 이 이중화다.

## 16.3 무한 루프의 기술 스택 구현: 배관, 작업대, 기억, 두뇌, 손발

이 장의 핵심 절이다. 1부 5장에서 우리는 DMAIC 데이터 루프 — 사람이 분기마다 돌리던 개선 사이클을 LLM 에이전트가 상시로 돌리는 무한 루프 — 를 방법론으로 설계했다. 그때의 다이어그램에서 각 단계는 "관리도 이상 → 문제 정의 → 3원천 수집 → 통계·그래프 분석 → 개선안 생성과 시뮬레이션 → 승인 게이트 → Odoo 환류"로 이어졌다. 방법론의 언어로 설계된 그 루프가, 이 장의 스택 위에서는 다음과 같은 역할 분담으로 실장된다.

루프를 신체에 비유하면 배치가 선명해진다. n8n은 배관이자 신경계다. 관리도 알람과 웹훅 트리거로 루프의 회전을 점화하고, 각 단계 사이에서 데이터를 옮기며(ETL), 단계의 산출을 다음 단계의 입력으로 전달한다. Dify는 작업대다. "원인 분석 에이전트", "개선안 생성 에이전트", "브리핑 생성 앱" 같은 루프의 지능 단계들이 Dify 위의 앱으로 만들어지고 버전 관리되고 관측된다. Neo4j는 기억이다. 온톨로지 지식그래프가 분석의 무대(경로 역추적·중심성)이자 회전의 침전물(확정된 원인 관계, 승인·기각의 이력)이 쌓이는 장소다. LLM은 두뇌다. Ollama와 Claude의 이중화 구성이 가설을 생성하고 서사를 종합하되, 언제나 그래프의 사실과 통계의 검정 위에서만 말한다. 그리고 Odoo는 손발이다. 루프의 결론 — 재주문 규칙의 파라미터, 라우팅 마스터, 검사 포인트, 승인 워크플로 — 이 Odoo의 상태 변경으로 환류되어 다음 트랜잭션부터 즉시 작동한다. 5장의 명제, "표준화가 문서로 저장되면 소멸하고 시스템의 상태로 저장되면 지속된다"의 기술적 실현이다.

| DMAIC 단계 | 5장의 방법론 정의 | 담당 스택 | 구체 구현 |
|------|------|------|------|
| Define | 관리도 이상·경영 질문 → 문제 정의문 | n8n + Dify | n8n 크론·웹훅이 KPI 관리도 감시, 이상 시 Dify '문제정의 에이전트' 호출 |
| Measure | 3원천 상시 수집과 신뢰성 검증 | Odoo + n8n | 트랜잭션·POP은 Odoo가, 외부·센서는 n8n이 수집, 검증 규칙은 n8n 파이프라인에 내장 |
| Analyze | 통계 검정 × ML × 그래프 역추적 | Neo4j + LLM | Cypher 경로·중심성 분석, 통계 노드, LLM의 가설 생성(GraphRAG 근거 제시) |
| Improve | 개선안 생성 → What-if 비교 | LLM + frePPLe | Dify 에이전트가 대책 후보 초안, frePPLe 시나리오가 성적표 산출 |
| 승인 게이트 | Human-in-the-Loop | Odoo + Dify | Odoo 활동(Activity)·승인 워크플로로 상신, 수정·기각 사유가 그래프에 적재 |
| Control | 마스터·규칙 환류와 상시 감시 | Odoo + n8n | n8n이 승인안을 Odoo API로 반영, 신설 관리도를 감시 대상에 등록 |

한 회전을 이어 붙이면 이렇게 된다. 납기준수율 관리도가 한계선을 벗어나면 n8n의 감시 워크플로가 이를 감지해 Dify의 문제정의 에이전트를 호출하고, 에이전트는 문제 정의문 초안을 만들어 Odoo의 승인 활동으로 상신한다. 승인되면 n8n이 관련 데이터의 신뢰성 점검을 돌리고, 분석 에이전트가 Neo4j에서 층별·역추적·중심성 질의를 실행해 원인 가설을 세우며, 통계 검정을 통과한 가설에 대해 개선안 생성 에이전트가 대책 후보를 초안하고 frePPLe 시나리오로 성적표를 받는다. 사람이 승인 게이트에서 결정하면, n8n이 그 결정을 Odoo의 마스터와 규칙으로 환류하고 새 관리도를 감시 목록에 올린다. 회전의 전 과정 — 어떤 데이터에서 어떤 분석으로 어떤 제안이 나왔고 누가 어떻게 결정했는가 — 은 n8n의 실행 로그와 그래프의 이력 노드로 남아 감사 가능성과 재학습 재료를 동시에 충족한다. 5장에서 방법론으로 요구한 안전장치들 — 승인 게이트, 검정의 형식 요건화, 회전·변경 한도의 서킷 브레이커 — 이 각각 Odoo 워크플로, 파이프라인의 검정 노드, n8n의 조건 분기와 실행 한도로 구현되는 것이다.

이 구현에서 컨설턴트가 지켜야 할 설계 원칙은 하나다. 지능은 교체 가능하게, 기억과 배관은 안정되게. LLM은 몇 달 주기로 더 나은 모델이 나오는 소모성 부품이지만, 온톨로지와 코드체계, ETL 파이프라인은 기업의 축적 자산이다. 루프의 가치가 쌓이는 곳은 두뇌가 아니라 기억이라는 것 — 이것이 모델 경쟁의 소음 속에서 아키텍처가 흔들리지 않게 하는 중심추다.

## 16.4 성숙도 단계별 도입 순서: 어느 단계에서 무엇을

부스터를 한꺼번에 세우는 것은 이 아키텍처의 가장 흔한 오용이다. 1부 7장의 성숙도 5단계 — 기술(Descriptive), 진단(Diagnostic), 예측(Predictive), 처방(Prescriptive), 자율(Autonomous) — 는 기술 도입의 순서이자 신뢰 축적의 순서였다. 부스터의 도입 시점은 이 사다리에 정확히 대응한다.

| 성숙도 | 이 단계의 질문 | 도입하는 부스터 | 도입하지 말아야 할 것 |
|------|------|------|------|
| 1 기술 | 무엇이 일어났는가 | 부스터 없음. Odoo 단독 + n8n 최소(외부 채널 수집) | Neo4j·frePPLe — 데이터 품질 확보가 먼저 |
| 2 진단 | 왜 일어났는가 | Neo4j 온톨로지 + n8n ETL 본격화 + GraphRAG 질의 | 예측 모델 — 역추적이 안 되는 예측은 불신 |
| 3 예측 | 무엇이 일어날 것인가 | frePPLe 수요예측·보충 계획, ML 모델, Dify 질의 앱 | 자동 실행 — 예측 오차의 검증 기간 필요 |
| 4 처방 | 무엇을 해야 하는가 | frePPLe What-if 전면화, Dify 기반 DMAIC 루프 가동 | 승인 게이트 없는 환류 |
| 5 자율 | 검증된 것의 위임 | 신규 도입 없음. 승인 성적표 기반 자동화 범위 확대 | 성적표 없는 영역의 자동화 |

읽는 법은 두 방향이다. 순방향으로는, 각 부스터가 요구하는 기반이 앞 단계에서 마련된다. Neo4j에 적재할 가치가 있으려면 1단계에서 코드체계와 데이터 품질이 서 있어야 하고(적재되는 것이 혼돈이면 그래프는 혼돈의 지도일 뿐이다), frePPLe의 예측이 맞으려면 2단계까지의 실적 이력이 쌓여 있어야 하며, DMAIC 루프가 돌려면 3단계까지의 예측·분석 능력이 신뢰를 얻어 있어야 한다. 역방향으로는, 부스터는 질문이 요구할 때만 도입한다. 6장의 목표지향 설계가 가르쳤듯 모델은 언제나 마지막에 선택된다 — "왜"를 묻는 경영 질문이 쌓이기 전에 그래프를 세우는 것은 장식이고, 계획 최적화가 병목이 되기 전에 APS를 세우는 것도 장식이다. 실무적으로 n8n만은 예외적으로 이른 도입을 권한다. 1단계에서 외부 채널 수집의 배관으로 시작해 두면, 이후 모든 단계의 확장이 같은 캔버스 위의 워크플로 추가로 처리되기 때문이다. 확장의 최종 단계로, 센서 기반 예지보전이 필요해지는 시점에는 UMH(United Manufacturing Hub) 같은 산업 IoT 스택을 2단계 확장으로 더한다(이형근, 2026). 처음부터 모든 것을 세우지 않고 경영의 질문이 자라는 속도에 맞춰 부스터를 더하는 것 — 이것이 목표지향 설계의 아키텍처적 표현이다.

## 16.5 하이브리드 보안과 비용 구조: 데이터 주권을 구독료로

이 스택을 초소형 기업까지 확장한 관리형 클라우드 모델의 설계 철학은 "1인이 운영하는 시스템이 아니라, 1인을 운영해 주는 시스템"으로 요약된다(이형근, 2026). 서버를 모르는 사장에게 운영·보안·백업·업데이트를 관리형 클라우드가 통째로 떠안되, 데이터 민감도로 경계를 긋는 하이브리드 보안 모델을 취한다.

| 구분 | 관리형 공동 계층 | 고객 격리 계층 |
|------|------|------|
| 내용 | 자체 LLM 추론(GPU 공유), 공통 지식(상품분류·택배·세무 상식), 자동화 엔진(n8n), 보안·백업·업데이트 | 매출·정산 데이터, 고객 개인정보, 거래처·원가, 사업자 고유 노트(전용 암호화 DB) |
| 원리 | 다수가 비용 분담 → 1인 기업도 자체 LLM 사용 | 분리·암호화 → 유출·혼입 차단 |

핵심 명제는 "내 데이터는 내 금고에, 무거운 AI는 공동 발전소에서"다. GPU를 공동 운영하므로 1인 사업자도 구독료로 자체 LLM을 쓸 수 있고, 자체 LLM이므로 민감 데이터가 외부 API로 나가지 않는다. 여기에 Passkey(생체 인증) 로그인, 종단간 암호화, 자동 스냅샷 백업과 랜섬웨어 격리 보관, 무중단 자동 패치가 결합되어 "보안을 잘하라"가 아니라 "신경 쓸 일이 없게" 만드는 것을 지향한다. 제안서는 보안 사고의 다수가 패치·설정·백업의 문제에서 비롯되는 만큼 이 구조가 사고 원인을 구조적으로 제거한다고 주장한다(이형근, 2026). 데이터 주권의 관점에서 이 모델은 클라우드의 편의와 온프레미스의 통제 사이의 실용적 절충이다. 개인정보 보호와 AI 관련 법제가 강화되는 흐름 속에서, "우리 회사의 민감 데이터가 어느 국경과 어느 사업자의 서버를 거치는가"에 답할 수 있는 구조 자체가 기업의 신뢰 자산이 된다.

비용 구조도 같은 철학 위에 선다. 전 구성 요소가 오픈소스·소스 공개형이므로 소프트웨어 라이선스는 0원이고, 자체 LLM·자동화·보안·백업을 포함한 규모별 월 구독제로 초기 투자가 제거된다. 초소형 사업자의 AI 도입을 막는 최대 장벽이 초기 비용이라는 조사(중소기업중앙회, 2024)를 정면으로 겨냥한 구조이며, 6장 6.11절의 3주 경량 모델 — 온보딩·지식적재·현장적용 — 이 이 비용 구조 위에서 성립한다. 다만 컨설턴트는 고객에게 정직해야 한다. 라이선스 0원은 총비용 0원이 아니다. 뒤의 16.8절에서 보듯 이 스택의 진짜 비용은 라이선스가 아니라 통합과 운영에 있으며, 구독료는 그 운영을 누군가 대신 감당하는 값이다.

## 16.6 손끝의 서드브레인: 모바일·스마트글라스 시나리오

이 스택의 사용자 접점은 PC 화면이 아니라 폰과 스마트글라스다. 음성·사진·터치로 들어가 답으로 돌아오는 한 루프 — 제안서의 세 시나리오는 이 아키텍처가 현장에서 어떻게 체감되는지를 보여준다(이형근, 2026).

> **사례 — 1인 온라인 셀러의 하루.** 07:30, 침대에서 모바일로 밤사이 주문 14건의 자동 수집 브리핑을 받는다. '이어폰 품절 임박, 발주 권장' 알림에 "50개 발주서"라고 한마디 하면 발주 초안이 생성된다. 10:00, 작업대에서는 글라스 시야에 주문 송장과 품목이 표시되어 양손은 포장에 집중한다. 바코드 불일치는 즉시 경고되어 오출고가 사라지고, "완료" 음성에 송장이 자동 발급된다. 15:00, 카페에서 CS 12건의 자동 분류·답변 초안을 검토한다. 배송 문의 7건은 송장이 자동 첨부되었고, 까다로운 2건만 직접 확인해 일괄 발송한다.

> **사례 — 5인 미만 제조 사장의 하루.** 08:00 출근길, "오늘 뭐부터?"라는 음성 질문에 'OO정밀 브래킷 D-2, 알루미늄 재고 부족, 5번 품목 불량 2건'이라는 한 문장 브리핑이 돌아온다. 11:00 작업대의 글라스에는 도면 옆에 BOM·작업표준·과거 불량 포인트가 표시된다. 불량이 나면 사진 한 장 — LLM이 부위를 판독해 이력을 기록한다. 17:00, "정리해줘" 한마디에 완성 120개, 불량률 1.6%, 자재 입고, 내일 1순위까지 장부·재고·일정이 자동 정리된다.

> **사례 — 1~2인 물류의 하루.** 09:00 입고장, 글라스가 박스를 보면 품목·수량·보관 위치를 자동 인식하고 "A-03로" 음성 한마디로 입고가 끝난다. 11:00 피킹, 출고 80건의 최단 동선이 안내되고 선반 앞에 '이 칸 3개'가 표시되며 오피킹은 즉시 경고된다 — 초보도 첫날부터 베테랑처럼 움직인다. 16:00 이동 중, "출고 현황?" 질문에 76건 완료, 미출고 4건(2건 재고 부족), 지연 1건의 사유가 답으로 오고 셀러용 리포트가 자동 생성된다.

세 시나리오의 공통 구조에 주목할 필요가 있다. 인터페이스는 다르지만 — 모바일 브리핑, 글라스 증강, 음성 질의 — 그 아래에서 작동하는 것은 동일한 스택, 즉 Odoo의 기록, n8n의 자동화, Dify와 자체 LLM의 지능, 그래프의 문맥이다. 세그먼트별로 격리 계층의 운영 앱만 갈아 끼우고(온라인 판매는 주문통합·정산, 제조 소공인은 자재·BOM·작업지시, 물류는 WMS) 공동 계층의 AI·자동화·보안은 재사용하므로, 한 시스템이 세 업종을 커버하고 1인에서 5인, 50인으로 무중단 확장된다(이형근, 2026). 3장에서 논한 "기록이 작업의 일부가 되게 하라"는 수집 설계 원칙의 극한 형태가 여기 있다. 음성과 시선이 입력 장치가 되는 순간, 기록 행위는 사실상 소멸하고 데이터의 정량 — 실시간 전수 수집 — 이 부산물로 달성된다.

## 16.7 컨설팅 가이드: 진단 질문, 구축 순서, 성공 판정

### 부스터별 진단 질문 체크리스트

부스터 도입 상담에서 컨설턴트가 던져야 할 질문은 "이 기술이 필요한가"가 아니라 "이 기술이 답할 경영 질문과 그 기반이 있는가"이다. 다음 열 개의 질문으로 진단한다.

1. (공통) 현재 Odoo — 또는 동급의 단일 플랫폼 — 의 데이터 품질은 성숙도 1단계를 통과했는가. 재고 정확도 95% 이상, 월 마감의 시스템 완결이 확인되는가.
2. (공통) 이 부스터가 답할 경영 질문이 KGI-질문-KPI 트리(6장) 위에 문장으로 존재하는가.
3. (frePPLe) 계획 담당자가 엑셀로 일정을 짜는 데 주당 몇 시간을 쓰며, 납기 회답에 몇 시간이 걸리는가. 병목 자원이 어디인지 데이터로 답할 수 있는가.
4. (frePPLe) BOM 정확도와 공정 라우팅·표준시간 데이터는 유한능력 계산을 견딜 수준인가(13장의 판정 기준).
5. (n8n) 시스템 경계를 사람이 잇고 있는 지점 — 재입력, 복사·붙여넣기, 주기적 엑셀 취합 — 이 어디이며 월 몇 시간인가.
6. (Dify) 반복적으로 발생하는 질의·초안 업무(CS 답변, 견적 설명, 작업표준 문의)의 건수와 처리 시간은 얼마인가.
7. (Neo4j) "왜"를 묻는 질문 — 원인 역추적, 파급 분석 — 이 경영 질문 목록에 몇 개 있으며, 지금은 누가 어떻게 답하는가.
8. (LLM 이중화) 외부 API로 나가면 안 되는 데이터의 범위를 회사가 정의하고 있는가. 정의가 없다면 그것부터가 컨설팅 과제다.
9. (공통) 이 스택의 운영을 감당할 주체 — 내부 겸직자, 외부 파트너, 관리형 서비스 — 가 지정되어 있는가.
10. (공통) 부스터 도입의 성공을 판정할 KPI 기준선이 측정되어 있는가.

### 구축 순서와 기간

50인 이하 제조기업이 성숙도 2~4단계를 목표로 부스터를 얹는 표준 일정은 다음과 같다. 6장 5단계 로드맵의 4단계(지능화)를 부스터 관점에서 상세화한 것이다.

| 주차 | 작업 | 산출물 |
|------|------|------|
| 1~2주 | n8n 설치, Odoo 웹훅·API 연결, 첫 ETL(마스터→그래프) | 가동 중인 파이프라인 1본 |
| 3~6주 | 온톨로지 스키마 설계(경영 질문 기반), Neo4j 적재·동기화 | 스키마 정의서, 질의 가능한 그래프 |
| 5~8주 | Dify 구축, GraphRAG 질의 앱, LLM 이중화 라우팅 설정 | 자연어 질의 서비스(근거 제시형) |
| 7~10주 | frePPLe 커넥터 연동, 데이터 검증, 계획 시나리오 훈련 | 유한능력 계획 보드 |
| 11~12주 | DMAIC 루프 시범 가동(첫 경영 질문 1개), 승인 게이트 구성 | 루프 1회전 기록 보고서 |

기간은 데이터 성숙도에 따라 절반이 되거나 두 배가 된다. 특히 3~6주 차의 온톨로지 설계가 전체의 관문이다 — 여기서 부실하면 이후 모든 층이 부실해진다.

### 성공 판정과 흔한 실패

성공 판정은 부스터별로 하나씩이다. frePPLe는 계획 수립 시간과 납기 회답 시간의 단축(예: 주 8시간→1시간, 회답 반나절→10분), n8n은 수작업 연계 시간의 소멸, Dify·Neo4j는 경영 질문 응답 커버리지와 근거 추적 가능성(6장 4단계 판정 기준의 계승), 루프 전체로는 첫 회전의 완주 — Define부터 Control까지 사람의 승인 게이트를 거쳐 Odoo 환류가 실제로 일어났는가 — 다. 흔한 실패는 세 가지다. 첫째, 기술 선행 — 질문 없이 그래프부터 세우고 적재할 의미를 찾아 헤매는 경우로, 대응은 6장 1단계로의 회귀뿐이다. 둘째, 파이프라인 방치 — ETL이 조용히 실패하는데 아무도 모르는 상태로, 파이프라인 자체를 감시 대상 KPI로 등록하는 것이 회피법이다. 셋째, 시범 루프의 과욕 — 첫 DMAIC 루프에 가장 어려운 문제를 태우는 경우로, 첫 회전은 데이터가 두텁고 이해관계가 단순한 KPI(예: 특정 품목군의 재고회전)로 시작해 성공 체험을 만드는 것이 옳다.

## 16.8 정직한 평가: 복잡성의 값

이 아키텍처의 강점은 지금까지 충분히 논했으므로, 이 절은 약점에 집중한다. 첫째, 운영 복잡도다. Odoo, frePPLe, n8n, Dify, Neo4j, Ollama — 최소 여섯 개의 구성 요소는 각자의 버전 주기, 각자의 업그레이드 리스크, 각자의 장애 모드를 갖는다. 단일 상용 스위트라면 벤더가 감당할 통합 시험을 이 스택에서는 도입자가 감당한다. Odoo의 메이저 업그레이드가 frePPLe 커넥터의 호환성 검증을 요구하고, n8n 워크플로가 참조하는 API 스키마가 바뀌면 배관이 조용히 새기 시작한다. 관리형 서비스나 파트너 계약 없이 자체 구축한다면, 이 통합 유지보수를 감당할 최소한의 기술 역량 — 현실적으로 겸직 1인 이상과 외부 파트너의 조합 — 이 도입의 전제 조건이다.

둘째, 숨은 비용이다. 라이선스 0원의 이면에는 구축 인건비, 파트너 비용, GPU 비용(자체 LLM), 그리고 가장 큰 항목인 학습 곡선이 있다. 셋째, 책임 소재의 분산이다. 상용 스위트는 장애 시 전화할 곳이 하나지만, 이 스택은 문제가 경계에서 발생할 때 — 데이터가 그래프에 늦게 도착한 것이 n8n 탓인가 Neo4j 탓인가 — 원인 규명 자체가 일이 된다. 관측 가능성(로그·모니터링)의 설계를 구축 첫날부터 포함해야 하는 이유다. 넷째, 성숙도의 전제다. 이 장의 모든 약속은 1~3단계의 기반 위에서만 성립한다. 데이터 품질이 무너진 회사에 부스터를 얹는 것은 혼돈에 확성기를 다는 일이다.

그렇다면 누구에게 권하는가. 판단 기준은 세 가지다. ①단일 상용 스위트의 라이선스를 감당할 수 없거나 감당할 의사가 없는 규모(대체로 50인 이하)이면서, ②데이터 주권 — 민감 데이터의 외부 반출 통제 — 을 구조적으로 요구하며, ③운영을 감당할 파트너 또는 관리형 서비스를 확보할 수 있는 기업. 셋 중 하나라도 결여되면 대안을 보라. ①이 결여된 중견 이상이라면 상용 APS·BI의 병립도 관리 역량에 따라 유효하고, ③이 결여된 초소형이라면 자체 구축이 아니라 관리형 클라우드 구독(6장의 3주 경량 모델)이 답이다. 아키텍처는 이념이 아니라 적합성의 문제다 — 이 문장으로 부스터 논의를 닫고, 다음 장에서 2부 전체를 하나의 컨설팅 로드맵으로 결산한다.

## 핵심 요약

- 도메인별 전문 시스템의 병립은 데이터 3정5S를 시스템 경계에서 무너뜨리는 '시스템의 군도'를 낳는다. 원플랫폼+쓰리부스터는 단일 Odoo 원천 위에 계획(frePPLe)·AX(n8n+Dify)·지식(Neo4j GraphRAG) 부스터를 얹고, 오픈소스 구성으로 라이선스 0원과 IT 전담 0~1명 운영을 지향한다.
- LLM은 이중화한다. 민감·일상 과업은 Ollama 기반 자체 모델이, 익명화된 고난도 과업은 Claude 등 프론티어 모델이 맡으며, Dify·n8n의 모델 추상화가 종속을 구조적으로 회피한다.
- 1부 5장의 LLM 무한 루프는 이 스택 위에서 실장된다. n8n이 배관(트리거·ETL·환류 실행), Dify가 작업대(에이전트 앱), Neo4j가 기억(온톨로지·이력), LLM이 두뇌(가설·서사), Odoo가 손발(마스터·규칙의 상태 변경)이다. 지능은 교체 가능하게, 기억과 배관은 안정되게 설계한다.
- 부스터는 성숙도 사다리에 맞춰 도입한다. 1단계 기술은 Odoo 단독(+n8n 최소), 2단계 진단에서 Neo4j, 3단계 예측에서 frePPLe 예측·ML, 4단계 처방에서 What-if와 DMAIC 루프, 5단계 자율은 신규 도입이 아니라 성적표 기반 위임 확대다. 부스터는 질문이 요구할 때만 세운다.
- 하이브리드 보안 모델은 "내 데이터는 내 금고에, 무거운 AI는 공동 발전소에서"로 요약된다. 공동 계층이 비용을, 격리 계층이 보안을 해결하며, 월 구독제가 초기 비용 장벽을 제거한다. 모바일·스마트글라스 시나리오(1인 셀러·5인 제조·1~2인 물류)는 같은 스택 위에서 운영 앱만 바꿔 작동한다.
- 컨설팅은 부스터별 진단 질문 10항으로 기반과 질문의 존재를 확인한 뒤, 약 12주의 표준 순서(n8n→온톨로지→Dify·GraphRAG→frePPLe→루프 시범 가동)로 구축하고, 부스터별 단일 KPI와 루프 첫 회전의 완주로 판정한다.
- 정직한 평가: 여섯 개 구성 요소의 통합·운영 복잡도, 숨은 비용, 책임 소재의 분산이 이 아키텍처의 값이다. 규모·데이터 주권 요구·운영 파트너의 세 조건을 충족하는 기업에게만 권하며, 조건이 결여되면 상용 병립 또는 관리형 구독이 대안이다.
