# 제19장. 품질 부문: 불량률 감소의 온톨로지

> "품질 달성을 위해 대량 검사에 의존하는 것을 중단하라. 처음부터 품질을 제품 안에 만들어 넣음으로써 검사의 필요 자체를 없애라." — W. 에드워즈 데밍, 『Out of the Crisis』 14개 원칙 중 제3원칙 (Deming, 1986)

품질은 제조의 하위 항목이 아니라 독립된 경영 부문이다. 불량 하나는 재작업 비용으로 끝나지 않는다. 그것은 납기를 흔들고, 클레임이 되어 고객 신뢰를 깎고, 최악의 경우 리콜이 되어 회사의 존속을 위협한다. 그런데 불량만큼 '관계'가 본질인 데이터도 없다. 불량은 언제나 어떤 자재가, 어떤 설비에서, 어떤 조건으로, 누구의 손을 거쳐 만들어졌는가의 교차점에서 발생하기 때문이다. 개별 검사 성적서는 이 교차점을 담지 못한다. 이 장은 불량을 고립된 사건이 아니라 그래프 위의 경로로 다루는 방법 — 불량률 감소의 온톨로지 — 를 제3부 공통 형식에 따라 설계한다.

## 19.1 품질 부문의 경영 질문과 KPI 트리

품질 부문의 경영 질문은 세 겹이다. 첫째, **"우리는 지금 얼마나 잃고 있는가"** — 불량이 만드는 비용의 총량. 둘째, **"불량은 왜 발생하는가"** — 원인의 규명과 재발 방지. 셋째, **"문제가 터졌을 때 얼마나 빨리 범위를 특정할 수 있는가"** — 추적성과 리콜 대응력. 세 질문을 지표로 전개하면 다음의 KPI 트리가 된다.

```
불량률 감소 (KGI: COPQ 절감, 클레임 제로)
├─ 불량률(PPM: Parts Per Million, 백만 개당 불량 수)
│   ├─ 공정 불량률(공정별·설비별·로트별)
│   └─ 유출 불량률(출하 후 발견 — 클레임률·필드 불량)
├─ 초도수율(FPY: First Pass Yield, 재작업 없이 1회 합격한 비율)
│   └─ 누적수율(RTY) = 각 공정 FPY의 곱
├─ 공정능력지수(Cp/Cpk) — 산포와 치우침의 능력
├─ COPQ(Cost of Poor Quality, 품질실패비용)
│   ├─ 내부 실패(폐기·재작업·재검사)
│   ├─ 외부 실패(클레임·반품·리콜·신뢰 손실)
│   └─ (예방·평가 비용과의 균형)
└─ 원인 규명 리드타임(불량 발견→원인 확정→조치 완료)
```

각 지표의 정의를 정확히 하자. **PPM**은 불량 수를 검사 수량으로 나눠 백만 배 한 값으로, 퍼센트로는 표현이 무뎌지는 낮은 불량 수준을 다루기 위한 단위다(1% = 10,000 PPM). **FPY(초도수율)**는 재작업·수리를 거치지 않고 첫 시도에 합격한 비율로, 재작업을 거쳐 최종 합격한 것까지 포함하는 최종수율과 구분해야 한다. 재작업이 많은 공장은 최종수율이 높아도 FPY가 낮으며, 그 차이가 숨은 공장(hidden factory)의 크기다. 공정별 FPY의 곱인 누적수율(RTY)은 공정이 길수록 급격히 떨어진다 — FPY 98%짜리 공정 열 개를 통과하면 RTY는 81.7%다.

**공정능력지수**는 규격 폭과 공정 산포의 비율이다.

```
Cp  = (USL − LSL) / 6σ            (USL·LSL: 규격 상·하한, σ: 공정 표준편차)
Cpk = min[ (USL − μ) / 3σ , (μ − LSL) / 3σ ]   (μ: 공정 평균)
```

Cp는 산포만을, Cpk는 평균의 치우침까지 반영한다. 공정이 규격 중심에 정렬되어 있을 때 Cp 1.00은 약 2,700 PPM, 1.33은 약 63 PPM에 대응하며, 통상 1.33이 양산 공정의 최소 기준으로 쓰인다(Montgomery, 2013). Cpk가 Cp보다 뚜렷이 낮다면 문제는 산포가 아니라 치우침이므로 조치의 방향이 달라진다 — 지표의 분해가 곧 진단이라는 점에서 OEE와 같은 구조다.

**COPQ**는 품질 문제가 만드는 총비용이다. 파이겐바움이 예방(prevention)-평가(appraisal)-실패(failure)의 범주로 품질비용을 체계화한 이래(Feigenbaum, 1956), 주란은 눈에 보이지 않는 실패비용을 "광산 속의 금(gold in the mine)"이라 불렀다(Juran, 1951). 폐기·재작업 같은 내부 실패는 장부에 보이지만, 클레임 대응 공수, 긴급 물류비, 잃어버린 재주문 같은 외부 실패는 대부분 계정과목 어디에도 없다. COPQ를 KPI 트리에 올리는 이유는 품질 투자의 의사결정 — 검사를 강화할 것인가, 공정을 개선할 것인가 — 을 비용의 언어로 번역하기 위해서다. 이 판단은 19.4절의 What-if에서 다시 다룬다.

## 19.2 Odoo에서 발생하는 품질 데이터 지도

Odoo의 품질(Quality) 모듈은 제조·재고와 같은 데이터베이스 위에서 작동하므로, 품질 데이터는 태어나는 순간부터 로트·공정·설비 데이터와 연결될 조건을 갖추고 있다.

| 온톨로지 개념 | Odoo 원천(모델) | 발생 이벤트·주요 필드 | 연결 KPI |
|---|---|---|---|
| 검사 기준 | quality.point (QCP) | 공정·품목별 관리 포인트, 검사 유형·주기 | 평가 비용 |
| 검사 실적 | quality.check | 합부 판정, 측정값, 사진 첨부 | PPM, FPY, Cp/Cpk |
| 품질 경보 | quality.alert | 불량 내용, 원인·조치 기록, 담당 배정 | 원인 규명 리드타임 |
| 로트·시리얼 | stock.lot | 자재 로트 소비, 완성 로트 생산의 연결 | 추적성, 리콜 범위 |
| 폐기·재작업 | stock.scrap, 재작업 MO | 폐기 수량·사유, 재작업 오더 | COPQ 내부 실패 |
| 공정·설비 맥락 | mrp.workorder, maintenance | 어느 설비·작업자·시각에 만들었는가 | 원인 추론 |
| 수입검사 | 매입 입고 + QCP | 공급업체 로트 합부 이력 | 공급업체 품질 점수 |
| 클레임·반품 | 헬프데스크, 반품 오더 | 고객 불만, RMA, 필드 불량 | 유출 PPM, 외부 실패 |
| 변경 이력 | PLM ECO, 인사·근태 | 설계 변경, 금형·자재·작업자 교체 | 4M 변경점 |

지도에서 확인할 핵심은 두 가지다. 첫째, PPM·FPY는 검사 실적에서, Cp/Cpk는 측정값에서, COPQ는 폐기·재작업·클레임에서 나온다 — 품질 KPI 전체가 표준 트랜잭션만으로 산출 가능하다. 둘째, 그러나 원인 규명에 필요한 것은 품질 모듈 바깥에 있다. 불량 로트가 소비한 자재 로트는 재고 모듈에, 그 로트를 만든 설비와 작업자는 제조 모듈에, 최근의 금형 교체는 유지보수 모듈에 있다. 기록은 한 데이터베이스에 있지만 **관계는 암묵적**이다. 이 암묵적 관계를 명시적 그래프로 끌어올리는 것이 품질 온톨로지의 역할이다.

## 19.3 온톨로지 설계: 불량-원인-공정-자재-설비 그래프와 5축 고장코드

품질 온톨로지의 어휘는 코드체계에서 시작한다. 제5장에서 소개한 5축 고장코드는 하나의 불량 사건을 다섯 개의 독립된 축으로 기술하는 체계다(이형근, 2026). 축이 분리되어 있다는 점이 핵심이다 — "프레스크랙"처럼 공정과 현상이 한 덩어리로 붙은 코드는 집계도 추론도 불가능하지만, 축이 분리된 코드는 어떤 축으로도 자르고 묶을 수 있는 다차원 데이터가 된다.

```
[5축 고장코드 — 하나의 불량 사건을 다섯 축으로 기술한다]

 축1 공정(Where-Process) : 어느 공정에서 발견되었는가    예) PR03 = 3번 프레스 공정
 축2 부위(Where-Position): 제품의 어느 부위인가           예) FLG.L = 좌측 플랜지
 축3 현상(What-Mode)     : 무엇이 관찰되었는가            예) CRK = 크랙, SCR = 스크래치
 축4 원인계(Why-4M)      : 어느 원인 계열로 추정되는가     예) MC=설비, MT=자재, MN=사람, MD=방법
 축5 조치(How-Action)    : 어떻게 처리되었는가            예) RW=재작업, SC=폐기, UA=특채

 표기 예) PR03-FLG.L-CRK-MT-SC
 → "3번 프레스 공정에서 발견된 좌측 플랜지 크랙, 자재 기인 추정, 폐기 처리"
```

이 코드를 어휘로 삼아, 불량-원인-공정-자재-설비-작업자를 잇는 그래프 스키마를 다음과 같이 설계한다. 제18장의 제조 그래프와 노드를 공유한다는 점에 주의하라 — 품질 온톨로지는 별도의 그래프가 아니라 같은 그래프의 다른 관점이다.

```
[노드(Node) 정의 — 제18장 제조 그래프에 추가되는 품질 계층]
(:Defect     {id, code5, date, qty, photo})  불량 사건(5축 코드 보유)
(:DefectMode {code, name})                   현상 사전(축3: CRK, SCR, DIM...)
(:Cause      {code, category})               원인 사전(축4: 4M 분류 하위)
(:Inspection {id, result, value, spec})      검사 실적(측정값 포함)
(:ChangePoint{id, type, date, desc})         4M 변경점(설비·자재·사람·방법)
(:MaterialLot{id, recv_date})                자재 로트(수입검사 이력 연결)
(:Supplier   {code, name})                   공급업체
(:Claim      {id, customer, date, cost})     고객 클레임·필드 불량

[관계(Relationship) 정의]
(Defect)-[:FOUND_IN]->(Lot)                  어느 생산 로트에서
(Defect)-[:AT_OPERATION]->(Operation)        어느 공정에서(축1)
(Defect)-[:OF_MODE]->(DefectMode)            어떤 현상으로(축3)
(Defect)-[:ATTRIBUTED_TO {conf}]->(Cause)    어떤 원인으로(축4, 확신도 부여)
(Defect)-[:RESOLVED_BY]->(Action)            어떤 조치로(축5)
(MO)-[:CONSUMED]->(MaterialLot)<-[:SUPPLIED_BY]-(Supplier)
(Inspection)-[:CHECKS]->(Lot|MaterialLot)
(ChangePoint)-[:ON]->(Equipment|Operation|Worker|MaterialLot)
(Claim)-[:TRACED_TO]->(Lot)
```

원인 관계에 확신도(confidence) 속성을 두는 것은 의도적 설계다. 불량의 원인은 발견 시점에 확정되지 않는다. 처음에는 작업자의 추정(축4 코드)으로 기록되고, 이후 그래프 역추적과 통계적 검증을 거치며 확신도가 갱신된다. 원인 규명을 일회성 보고서가 아니라 **그래프 위에서 갱신되는 가설**로 다루는 것 — 이것이 종래의 품질 문서 관리와 온톨로지 접근의 결정적 차이다.

## 19.4 추론·판단 메커니즘

### 19.4.1 SPC 관리도 자동화

통계적 공정관리(SPC)는 슈하트가 관리도를 고안한 1920년대 이래 품질공학의 기둥이다(Shewhart, 1931). 공정의 산포를 우연 원인과 이상 원인으로 구분하고, 3σ 관리한계를 벗어나거나 비정상 패턴(연속 상승, 한쪽 쏠림 등 웨스턴일렉트릭 규칙)이 나타날 때만 개입한다는 원리는 지금도 유효하다. 문제는 운영이다. 많은 중소기업에서 관리도는 감사 때만 그리는 서류가 되어 있다. 자동화의 구조는 단순하다. Odoo 검사 실적(quality.check)의 측정값을 n8n이 수집해 품목·공정별 관리도 통계를 상시 갱신하고, 관리한계 이탈이나 런 규칙 위반이 감지되면 품질 경보(quality.alert)를 자동 생성하여 담당자에게 배정한다. 동시에 해당 이벤트는 그래프에 이상 신호 노드로 적재되어, 이후 불량이 실제로 발생했을 때 "불량 이전에 관리도가 보내던 신호"로 소급 연결된다. Cp/Cpk 역시 같은 데이터에서 주 단위로 자동 산출되어 공정 노드의 속성으로 갱신된다.

Quality 4.0 연구는 이 방향의 이론적 배경을 제공한다. 조넨샤인과 케네트는 4차 산업혁명 환경에서 품질공학이 검사 기반에서 데이터·예측 기반 분야로 재편되어야 한다고 주장했고(Zonnenshain & Kenett, 2020), 후속 리뷰는 Quality 4.0을 "인더스트리 4.0 역량과 품질경영 실무의 정렬"로 정의하며 IoT·빅데이터·AI·클라우드를 그 기술 스택으로 정리했다(Sader, Husti & Daróczi, 2022). 관리도의 자동화는 그 첫 계단이다 — SPC가 실시간으로 돌 때 비로소 예측 품질로 갈 데이터가 쌓인다.

### 19.4.2 비전 AI 불량 판독: 사진 한 장이 이력이 되기까지

불량 데이터의 최대 병목은 기록 그 자체다. 현장 작업자에게 불량 하나마다 코드 다섯 개를 고르라는 요구는 지속되지 않는다. 오픈브레인 세미나의 제조 시나리오는 이 병목을 사진 한 장으로 돌파한다. 작업자가 스마트글라스나 폰으로 불량품을 촬영하면, 멀티모달 LLM이 부위를 판독하고 — "좌측 플랜지 모서리, 길이 약 12mm의 크랙" — 5축 코드의 축1(현재 공정은 작업오더 맥락에서 자동), 축2(부위), 축3(현상)을 초안으로 부여하며, 작업자는 확인·수정만 한다(이형근, 2026). 판독 결과는 사진과 함께 불량 노드로 그래프에 기록된다. 기록 비용이 낮아지면 기록 건수가 늘고, 기록이 늘면 추론이 정확해지는 선순환이 시작된다.

정확도에 대한 정직한 주의가 필요하다. 품질 데이터는 극단적인 클래스 불균형 — 양품 사진은 넘치고 불량 사진은 희소하며, 불량 중에서도 희귀 모드는 더 희소한 — 을 갖는 것이 보통이며, 이는 제조 품질보증 머신러닝 연구들이 공통으로 지적하는 난점이다(Elsevier 체계적 리뷰, 2025). 따라서 초기에는 LLM 판독을 '자동 판정'이 아니라 '기록 보조'로 위치시키고, 사람의 확정 판정을 누적해 정확도를 검증한 뒤 단계적으로 자동화 범위를 넓히는 것이 옳다. 판정 책임은 사람에게 남는다 — 인간-AI 협업 루프의 품질 부문 버전이다.

### 19.4.3 그래프 역추적: 이 로트의 불량은 무엇과 연결되는가

원인 추론의 출발은 언제나 같은 질문이다. "이번 불량 로트는 어느 자재, 어느 설비, 어느 조건과 연결되어 있는가." 관계형 DB에서 이 질문은 예닐곱 개 테이블의 조인이지만, 온톨로지에서는 경로 탐색 하나다.

```cypher
// 최근 2주간 크랙(CRK) 불량이 발생한 로트들의 공통 연결 요소를 역추적한다
MATCH (d:Defect)-[:OF_MODE]->(:DefectMode {code:'CRK'})
WHERE d.date >= date() - duration('P14D')
MATCH (d)-[:FOUND_IN]->(l:Lot)<-[:YIELDS]-(mo:MO)
MATCH (mo)-[:HAS_WO]->(wo:WO)-[:RUN_ON]->(e:Equipment)
MATCH (mo)-[:CONSUMED]->(ml:MaterialLot)<-[:SUPPLIED_BY]-(s:Supplier)
OPTIONAL MATCH (cp:ChangePoint)-[:ON]->(e)
WHERE cp.date >= d.date - duration('P30D')
RETURN s.name  AS 공급업체, ml.id AS 자재로트,
       e.code  AS 설비,     cp.type AS 최근변경점,
       count(DISTINCT d) AS 불량건수
ORDER BY 불량건수 DESC
```

이 질의가 돌려주는 것은 확정된 인과가 아니라 **의심 순위**다. 크랙 불량 9건 중 7건이 특정 공급업체의 특정 입고 로트를 소비했고, 그 로트의 수입검사 측정값이 규격 하한에 붙어 있었다면, 자재 기인 가설의 확신도가 올라간다. 반대로 불량이 특정 설비에 집중되고 그 설비에 30일 내 금형 교체 변경점이 있다면 설비 기인 가설이 우세해진다. GraphRAG 위의 LLM은 이 경로들을 자연어로 종합한다 — "크랙 불량은 M사 7월 15일 입고 로트와 가장 강하게 연관됩니다. 다만 5번 프레스의 금형 교체와 시기가 겹치므로, 해당 자재를 다른 설비에서 가공한 로트의 불량률 확인을 권합니다." 다중 홉 관계 질의에서 그래프 기반 검색이 벡터 검색보다 강하다는 것은 GraphRAG 연구가 보인 바이며(Edge et al., 2024), 원인 추론은 그 전형적 활용례다. 중요한 것은 답과 함께 **근거 경로**가 제시되므로 품질 회의가 심증이 아니라 경로 위에서 진행된다는 점이다.

### 19.4.4 4M 변경점 관리

현장의 오랜 경험칙은 "불량은 바뀐 곳에서 나온다"이다. 사람(Man)·설비(Machine)·자재(Material)·방법(Method)의 4M 변경점을 기록하고 변경 직후를 집중 관리하는 것은 자동차 부품 업계 등에서 표준 관행이지만, 변경 기록이 수기 게시판에 머무는 한 불량과의 대조는 사람의 기억에 의존한다. 온톨로지에서 변경점은 일급 노드다. 설계 변경(PLM ECO), 금형·설비 수리(유지보수), 자재 로트 전환(재고), 작업자 교체(근태·배치)가 각각 ChangePoint 노드로 자동 생성되어 대상 노드에 연결된다. 그러면 두 가지 추론이 가능해진다. 사후적으로는 위 Cypher처럼 불량 발생 시 인근 변경점을 자동 소환하고, **사전적으로는 변경점 발생 시 검사 강화를 자동 발동한다** — 예컨대 신규 자재 로트 투입 후 첫 50개는 QCP 검사 주기를 촘촘히 바꾸는 규칙을 n8n이 Odoo에 적용하는 식이다. 변경점 관리가 자동화되면, 예방은 구호가 아니라 시스템의 기본 동작이 된다.

### 19.4.5 로트 추적성과 리콜 시뮬레이션

품질 부문의 세 번째 경영 질문 — 문제가 터졌을 때 범위를 얼마나 빨리 특정하는가 — 는 추적성의 질문이다. Odoo는 로트/시리얼 기준의 업스트림(완제품→자재)·다운스트림(자재→완제품→고객) 추적을 표준 제공하며, 온톨로지 그래프에서는 리콜 범위 산정이 전방 탐색 질의가 된다.

```cypher
// 문제 자재 로트가 흘러 들어간 완제품 로트와 출하 고객을 전방 추적한다
MATCH (ml:MaterialLot {id:'MAT-20260715-M3'})<-[:CONSUMED]-(mo:MO)
MATCH (mo)-[:YIELDS]->(l:Lot)-[:SHIPPED_IN]->(dv:Delivery)-[:TO]->(c:Customer)
RETURN c.name AS 고객, dv.id AS 출하번호, l.id AS 로트, dv.date AS 출하일
```

식품·바이오·자동차부품처럼 추적성이 규제 요건인 업종에서 이 질의의 응답 시간은 곧 리콜 비용의 크기다. 회수 대상이 전 생산분인가, 3개 로트 187개인가의 차이는 수억 원의 차이이며, 베트남 향신료 제조사 Dh Foods가 15개국 수출의 품질 신뢰 요건을 원재료-완제품-고객의 완전 추적성으로 충족한 사례가 보여 주듯(Odoo 공식 사례) 추적성은 수출 기업의 시장 진입 조건이기도 하다. 나아가 그래프 위에서는 리콜 '시뮬레이션'이 가능하다 — 실제 사고가 나기 전에 가상의 자재 로트 오염을 가정하고 회수 범위·소요 시간·대응 비용을 주기적으로 리허설하는 것이다. 소방 훈련을 데이터로 하는 셈이다.

### 19.4.6 What-if: 검사 강화인가, 공정 개선인가

품질 투자의 고전적 딜레마는 검사(유출 차단)와 개선(발생 차단) 사이의 배분이다. COPQ 구조와 온톨로지 데이터가 있으면 이 판단을 시뮬레이션할 수 있다. 다음은 공정 불량률 2.4%, 유출 1,200 PPM인 가상의 부품 제조사 예시로, 수치는 설명을 위한 것이다.

| 항목 | 시나리오 A: 검사 강화(전수검사) | 시나리오 B: 공정 개선(금형 보수 + SPC) |
|---|---|---|
| 투자·비용 | 검사 인력 증원 연 4,200만 원 | 금형 보수 2,500만 원 + SPC 구축 800만 원 |
| 유출 불량 | 1,200 → 300 PPM (차단) | 1,200 → 400 PPM (발생 감소의 결과) |
| 공정 불량 | 2.4% 유지 (불량은 계속 생산됨) | 2.4% → 1.1% |
| COPQ 변화(연) | 외부 실패 −1,900만 원, 내부 실패 불변 | 내부+외부 실패 합계 −5,200만 원 |
| 12개월 순효과 | −2,300만 원 (비용이 효과 상회) | +1,900만 원 |
| 비고 | 즉시 효과, 지속 비용 | 효과 발현까지 1~2개월, 효과 지속 |

이 구조가 보여 주는 것은 데밍의 제3원칙 그대로다 — 검사는 유출을 줄일 뿐 불량의 발생 비용을 줄이지 못하므로, 장기 균형은 대개 공정 개선 쪽에 있다. 그러나 클레임이 임박한 국면에서는 A를 임시 방어로 쓰고 B를 병행하는 것이 옳을 수 있다. 온톨로지의 기여는 정답의 제시가 아니라, 두 시나리오의 COPQ 궤적을 실제 자사 데이터로 계산해 **의견 대립을 수치 대립으로 바꾸는 것**이다.

## 19.5 실행 루프: 판단이 조치로 돌아오는 구조

품질 부문의 환류 루프는 불량 한 건의 생애주기를 따라 닫힌다.

```
[발생]  현장 불량 발견 — 사진 촬영(글라스/모바일)
   ↓
[기록]  LLM 부위 판독 → 5축 코드 초안 → 작업자 확인 → Odoo 품질경보 생성
   ↓  (n8n ETL)
[적재]  Neo4j — 불량 노드가 로트·공정·설비·자재·변경점에 연결
   ↓
[추론]  그래프 역추적(의심 순위) + SPC 신호 소급 + 유사 과거 사례 소환
   ↓
[판단]  "자재 기인 확신도 0.7 — M사 로트 격리, 대체 로트 투입,
        수입검사 강화 권고" (품질 담당 승인)
   ↓  (n8n 액션: Odoo API)
[환류]  로트 격리(재고), 공급업체 시정요구(매입), 검사 주기 변경(QCP),
        필요 시 설계 변경 발의(PLM ECO), 정비 요청(유지보수)
   ↓
[학습]  조치 후 해당 모드 PPM 추이 → 원인 확신도 갱신 → 노하우 노드화
```

운영 리듬에서 특기할 점은 원인 규명 리드타임을 KPI로 관리한다는 것이다. 불량률은 결과 지표이지만, 발견에서 조치까지의 시간은 품질 시스템 자체의 역량 지표다. 그래프에 발견·추론·승인·조치의 타임스탬프가 모두 남으므로 이 리드타임은 자동 측정된다. 그리고 종결된 불량 사건은 "이 현상-이 원인-이 조치가 효과 있었다"는 검증된 사례로 그래프에 남아, 다음 유사 불량에서 LLM이 첫 번째로 소환하는 조직 기억이 된다. 베테랑 품질 담당자의 은퇴와 함께 사라지던 판단 이력이 회사의 자산으로 남는 것 — 품질 온톨로지의 조용한, 그러나 가장 오래가는 효익이다.

| Novobi(Odoo 골드 파트너) 고객 집계 | 미국, 항공우주·제약·정밀제조 | Odoo Quality(QCP·경보·추적성) 도입 | 도입 첫해 스크랩·재작업 비용 25~40% 절감(파트너 집계, 개별사 미공개) | Novobi 보고 |

> **사례** 경남 의령의 대성종합열처리는 열처리 가공이라는, 공정 조건(온도·시간·냉각)이 품질을 좌우하는 전형적 뿌리산업 기업이다. 스마트공장 시스템으로 공정 데이터를 기록·관리하기 시작한 뒤 불량률을 50% 줄이면서 생산량을 75% 늘렸다. 주목할 것은 두 수치가 동시에 달성되었다는 점이다 — 불량 감소는 재작업과 폐기를 줄여 유효 생산능력을 키우므로, 품질 개선은 그 자체로 생산성 정책이다. 제18장의 OEE에서 품질 요소가 곱셈 항으로 들어가는 이유이며, 경남도 집계(2022~2023년 도입 439개사)에서도 품질 44.3% 향상과 원가 32.5% 절감이 나란히 보고되었다.

> **사례** LG전자 창원 스마트파크는 국내 가전 최초의 WEF 등대공장으로, 디지털 트윈을 품질 분석에 적용해 불량 원인 분석 시간을 50% 이상 단축하고 불량률을 30% 낮췄다. 대기업 사례지만 시사점은 규모와 무관하다 — 성과의 절반이 '불량률'이 아니라 '원인 분석 시간'에서 나왔다는 점이다. 원인 규명 리드타임이야말로 품질 시스템의 역량 지표라는 본 장의 주장과 정확히 일치하며, 그래프 역추적은 바로 이 시간을 며칠에서 몇 분으로 줄이는 메커니즘이다.

균형을 위해 덧붙이면, Novobi의 25~40% 절감 수치는 파트너사 집계로 개별 기업 검증이 공개되지 않은 추정 성격이며, 중기부의 품질 43.5%와 정책브리핑의 불량률 53%는 발표 시점·모수가 다른 수치이므로 혼용해서는 안 된다. 그러나 국내외 사례를 관통하는 패턴은 일관된다 — 품질 성과는 검사 인력의 증원이 아니라 **불량 데이터가 공정·자재·설비 데이터와 연결되는 순간**에 움직이기 시작했다.

## 19.7 도입 단계별 체크리스트

**1단계 — 진단(경영 질문 정의)**
- [ ] 현재 PPM·FPY·클레임률을 (부정확하더라도) 산출하고 최다 불량 모드 상위 5개를 파악했는가
- [ ] COPQ를 내부·외부 실패로 나눠 첫 추정을 해 보았는가(숨은 비용 포함)
- [ ] 5축 고장코드(공정·부위·현상·원인계·조치)를 현장 용어로 정의하고 현장 검증을 거쳤는가

**2단계 — 기반(Odoo 품질 구축)**
- [ ] 핵심 공정에 QCP(품질 관리 포인트)가 설정되고 검사 결과가 시스템에 직접 입력되는가
- [ ] 로트/시리얼 추적이 자재 입고부터 출하까지 끊김 없이 이어지는가(더미 로트 금지)
- [ ] 폐기·재작업이 사유 코드와 함께 기록되는가
- [ ] 클레임·반품이 로트 번호와 연결되어 접수되는가

**3단계 — 적재(데이터·지식)**
- [ ] 불량·검사·변경점 데이터가 n8n ETL로 그래프에 자동 적재되는가
- [ ] 4M 변경점(ECO·정비·자재 로트 전환·작업자 교체)이 자동으로 변경점 노드가 되는가
- [ ] 과거 중대 불량의 원인 규명 이력이 사례 노드로 소급 적재되었는가

**4단계 — 지능화(추론·판단)**
- [ ] SPC 관리도가 자동 갱신되고 이탈 시 품질 경보가 자동 생성되는가
- [ ] 사진 기반 LLM 불량 판독이 '기록 보조' 모드로 운영되며 정확도가 측정되는가
- [ ] 불량 발생 시 그래프 역추적 의심 순위가 자동 제시되는가
- [ ] 리콜 시뮬레이션(가상 로트 회수 리허설)을 분기 1회 이상 수행하는가

**5단계 — 환류(실행 루프)**
- [ ] 판단→조치(로트 격리·검사 강화·시정요구·ECO)가 Odoo 액션으로 자동 연결되는가
- [ ] 원인 규명 리드타임이 KPI로 측정·관리되는가
- [ ] 종결 사건의 원인 확신도와 조치 효과가 그래프에 갱신되어 다음 추론에 쓰이는가

## 핵심 요약

- 품질 부문의 경영 질문은 "얼마나 잃고 있는가(COPQ), 왜 발생하는가(원인), 얼마나 빨리 범위를 좁히는가(추적성)"이며, KPI 트리는 PPM·FPY·Cp/Cpk·COPQ·원인 규명 리드타임으로 전개된다.
- Cp는 산포를, Cpk는 치우침까지 반영하며(Cp 1.33 ≈ 63 PPM), FPY와 최종수율의 차이가 재작업이라는 숨은 공장의 크기다. COPQ는 품질 투자를 비용의 언어로 번역하는 지표다(Feigenbaum, 1956; Juran, 1951).
- 5축 고장코드(공정-부위-현상-원인계-조치)는 불량 사건을 다차원으로 기술하는 온톨로지 어휘이며, 품질 그래프는 제조 그래프와 노드를 공유하는 같은 그래프의 다른 관점이다.
- 판단 메커니즘은 SPC 관리도 자동화(Shewhart, 1931; Quality 4.0으로의 확장은 Zonnenshain & Kenett, 2020), 사진→LLM 5축 코드 초안의 비전 AI 판독, Cypher 역추적에 의한 원인 의심 순위, 4M 변경점의 자동 연계와 선제 검사 강화, 로트 전방 탐색에 의한 리콜 시뮬레이션이다.
- 검사 강화와 공정 개선의 배분은 COPQ What-if로 수치화할 수 있으며, 장기 균형은 대개 발생 차단(공정 개선) 쪽에 있다 — 데밍 제3원칙의 데이터 버전이다.
- 대성종합열처리(불량률 −50%·생산량 +75%), 솔젠트(이물 불량 −40%), LG 스마트파크(원인 분석 시간 −50%), 중기부 통계(품질 +43.5%)가 보여 주듯, 품질 성과는 불량 데이터가 공정·자재·설비와 연결될 때 움직이며, 원인 규명 리드타임 단축이 그 지렛대다.
