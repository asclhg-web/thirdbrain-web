# 제15장. 확장 부스터 — frePPLe·n8n·Dify·Neo4j

> "도메인마다 따로 세우지 않는다. 한 플랫폼 + 세 부스터." — 오픈브레인 시스템 제안서 (오픈브레인, 2026)

## 15.1 One Platform + Three Boosters 아키텍처

앞의 여덟 개 장에서 본 것처럼 Odoo는 웹사이트부터 회계까지 한 플랫폼으로 커버한다. 그러나 14장의 결론이 보여주듯, Odoo만으로는 도달하지 못하는 세 영역이 있다. 유한능력 기반의 정밀한 생산 계획, 시스템 간 데이터를 잇는 자동화 배관, 그리고 기업의 의미 구조를 이해하는 지식 계층이다. 오픈브레인 제안서는 이 결핍을 도메인별 전문 시스템의 병립 — MES 따로, APS 따로, BI 따로 세우는 전통적 접근 — 이 아니라, 단일 플랫폼에 세 개의 부스터를 얹는 방식으로 해결한다(오픈브레인, 2026). 이른바 원플랫폼+쓰리부스터(One Platform + Three Boosters)다.

```
┌─────────────────────────────────────────────────────┐
│ 지식 부스터   Neo4j 온톨로지 GraphRAG + LLM(Claude/Ollama) │ ← 3rd Brain
├─────────────────────────────────────────────────────┤
│ AX 부스터    n8n 워크플로 허브 + Dify 사내 AI 앱          │
├─────────────────────────────────────────────────────┤
│ 계획 부스터   frePPLe (APS — Odoo 공식 커넥터)            │
├─────────────────────────────────────────────────────┤
│ ONE PLATFORM  Odoo CE: ERP+MES+SCM — 단일 PostgreSQL   │ ← 2nd Brain
├─────────────────────────────────────────────────────┤
│ 현장 계층     작업자(개인지식DB·옵시디언)·설비·센서        │ ← 1st Brain
└─────────────────────────────────────────────────────┘
        환류: 데이터는 위로(ETL), 판단은 아래로(작업지시 환류)
```

이 구성의 원칙은 두 가지다. 첫째, 모든 부스터는 오픈소스이거나 소스 공개형이다. 50인 이하, 매출 50~300억 원 규모의 기업이 소프트웨어 라이선스 비용 없이, IT 전담 인력 0~1명으로 운영 가능한 표준 구성을 지향한다(오픈브레인, 2026). 둘째, 부스터는 플랫폼을 대체하지 않고 보강한다. 데이터의 원천은 언제나 Odoo의 단일 PostgreSQL이며, 부스터들은 그 위에서 계획을 정밀화하고, 흐름을 자동화하고, 의미를 부여한다. 데이터는 위로(ETL), 판단은 아래로(작업지시 환류) 흐르는 환류 루프가 전체를 관통한다.

## 15.2 계획 부스터: frePPLe — 유한능력의 세계로

12장에서 본 대로 Odoo의 제조 관리는 MPS와 간트 계획까지 지원하지만, 표준 스케줄러는 기본적으로 자원 능력의 제약을 정밀하게 반영하는 데 한계가 있다. 설비 8대, 작업자 12명, 자재 입고 일정이라는 유한한 제약 아래에서 수백 개 제조 오더의 최적 순서를 찾는 문제는 전문 APS(Advanced Planning and Scheduling, 고급 계획 및 스케줄링)의 영역이다.

frePPLe는 가장 널리 쓰이는 오픈소스 APS로, 자원 능력·인력 가용성·자재 가용성·리드타임의 제약을 모두 반영한 유한능력(finite capacity) 생산 계획과 스케줄을 생성한다(frePPLe 공식 문서). 수요예측(통계적 시계열 예측), 안전재고·보충 계획, 시나리오 비교(What-if)까지 계획 업무 전반을 포괄한다. 결정적으로 frePPLe는 Odoo 공식 커넥터를 제공한다. Odoo 앱스토어에 등록된 연동 모듈을 통해 Odoo의 품목·BOM·워크센터·판매 오더·재고 데이터를 frePPLe로 보내고, 계산된 계획 결과 — 제조 오더와 구매 오더 제안 — 를 다시 Odoo로 돌려받는다(frePPLe, Odoo integration 문서). ERP를 바꾸지 않고 계획 두뇌만 이식하는 구조다.

도입 형태도 유연하다. frePPLe는 커뮤니티 에디션을 오픈소스로 공개하고 상위 기능(고급 예측, 시나리오 관리 등)을 상용 에디션으로 제공하는 오픈코어 모델이므로, 소규모 제조라면 무료 에디션과 Odoo 커넥터만으로 유한능력 스케줄링을 시작할 수 있다. 계획 담당자는 웹 화면에서 자원별 부하, 지연 예상 오더, 자재 제약을 확인하고, 시나리오를 복제해 "야간 조를 추가하면", "이 오더를 외주로 돌리면" 같은 What-if를 비교한 뒤, 채택한 계획만 Odoo로 환류시킨다. 계획은 부스터에서, 실행과 기록은 플랫폼에서 — 역할 분담이 명확하다.

서드브레인 관점에서 frePPLe는 처방적 분석(무엇을 해야 하는가)의 첫 번째 상설 엔진이다. "이 주문을 받으면 납기를 지킬 수 있는가", "설비를 한 대 늘리면 리드타임이 얼마나 줄어드는가"라는 경영 질문에 시뮬레이션으로 답하는, 6장에서 정의한 디지털 트윈의 계획 차원 구현이며, 그 상세 활용은 18장에서 다룬다.

## 15.3 AX 부스터: n8n과 Dify — 자동화의 배관과 AI의 작업대

### n8n: 워크플로 허브이자 ETL 엔진

n8n은 페어코드(fair-code) 라이선스의 워크플로 자동화 플랫폼으로, 400개 이상의 시스템 연동 노드를 시각적 캔버스에서 조립해 자동화를 구축한다(n8n 공식 GitHub). 자체 서버에 설치(self-host)할 수 있어 데이터가 외부 SaaS를 거치지 않으며, 이 점이 Zapier류 클라우드 자동화 도구와의 결정적 차이다. 오픈브레인 아키텍처에서 n8n의 역할은 두 가지다. 첫째, ETL 파이프라인이다. Odoo의 트랜잭션 데이터를 추출·변환해 Neo4j 지식그래프에 적재하고, 센서·오픈마켓·택배사 같은 외부 소스의 데이터를 Odoo로 모은다. 둘째, 워크플로 허브다. "불량 보고가 등록되면 사진을 LLM에 보내 부위를 판독하고, 결과를 품질 레코드에 기록한 뒤 담당자에게 알림"과 같은 시스템 횡단 자동화를 코드 없이 구성한다.

주목할 것은 n8n의 AI 네이티브 진화다. LLM·에이전트·벡터 스토어 노드가 내장되어 워크플로 안에서 AI 판단 단계를 자연스럽게 끼워 넣을 수 있으며, 2024년 기준 전체 워크플로의 75%가 AI·LLM 연동을 포함하는 것으로 보고되었다(n8n, 2024년 리뷰). 자동화 배관과 AI 추론이 한 캔버스에서 만나는 것이다.

### Dify: 사내 AI 앱의 조립 라인

Dify는 오픈소스 LLM 애플리케이션 개발 플랫폼이다. 프롬프트 설계, RAG 파이프라인(문서 적재·청킹·검색), 에이전트 워크플로, 모델 관리와 관측(observability)을 하나의 시각적 작업대에서 제공하며, Docker로 자체 호스팅할 수 있다(Dify 공식 GitHub). OpenAI·Anthropic 같은 상용 모델과 Ollama로 구동되는 로컬 오픈소스 모델을 동일한 인터페이스로 바꿔 끼울 수 있다는 점이 핵심이다. 오픈브레인 구성에서 Dify는 사내 AI 앱의 조립 라인을 맡는다. 상품 FAQ 응대 봇, 작업표준 질의응답, CS 답변 초안 생성기 같은 업무별 AI 앱을 개발자 없이 만들고, 지식베이스(상품·FAQ·작업표준·거래처)를 RAG로 연결한다(오픈브레인, 2026). 14장의 Odoo AI가 ERP 내장형 지능이라면, Dify는 기업이 모델과 데이터를 스스로 통제하는 자가 호스팅 지능이다.

두 도구의 역할 경계를 정리해 두는 것이 좋다. n8n은 "언제 무엇을 실행할 것인가"의 흐름 제어에, Dify는 "어떻게 답할 것인가"의 지능 구성에 강하다. 실무에서는 n8n 워크플로가 이벤트를 감지해 Dify 앱의 API를 호출하고, Dify가 RAG와 LLM으로 판단한 결과를 n8n이 다시 Odoo 레코드에 기록하는 접속 패턴이 표준이 된다. 둘 다 자체 호스팅이 가능하므로 데이터가 관리 경계 밖으로 나가지 않으며, 라이선스 관점에서 n8n은 페어코드(내부 사용 무료, 상용 서비스 제공 제한), Dify는 오픈소스(일부 상용 조항 부가)라는 차이는 재판매 사업을 구상하는 파트너라면 확인해야 할 지점이다.

## 15.4 LLM 이중화: Ollama와 Claude

오픈브레인 아키텍처의 LLM 전략은 이중화다. 온프레미스(또는 전용 클라우드)의 오픈소스 소형 모델과 클라우드 프론티어 모델을 병용한다(오픈브레인, 2026). Ollama는 Llama·Qwen·Mistral 등 오픈소스 LLM을 자체 하드웨어에서 손쉽게 구동하게 해 주는 실행 환경으로, 프롬프트와 출력이 네트워크 밖으로 나가지 않아 데이터 주권을 확보하고 토큰당 API 비용을 제거한다(Ollama 공식 문서). 반면 복잡한 추론 — 다단계 원인 분석, 장문 보고서 생성, 코드 생성 — 은 Claude 같은 프론티어 모델의 능력이 여전히 앞선다.

따라서 실무 설계는 과업 민감도와 난이도의 2×2로 갈린다. 민감 데이터를 다루는 일상 과업(주문 분류, 불량 기록 구조화, 사내 문서 질의)은 자체 호스팅 소형 모델이, 민감 데이터를 제거하거나 익명화한 고난도 과업(경영 분석 보고서, 시나리오 해석)은 클라우드 프론티어 모델이 맡는다. Dify와 n8n이 모델 추상화 계층을 제공하므로, 이 라우팅은 애플리케이션 코드를 바꾸지 않고 설정으로 운영할 수 있다. 특정 모델·특정 사업자에 대한 종속을 구조적으로 회피하는 것 — 14장에서 지적한 Odoo AI의 범용 LLM 종속성에 대한 답이 바로 이 이중화다.

## 15.5 지식 부스터: Neo4j GraphRAG — 서드브레인의 본체

세 번째 부스터가 이 책의 핵심인 지식 계층이다. Neo4j는 대표적인 속성 그래프(property graph) 데이터베이스로, 노드(객체)와 관계(엣지)와 속성을 원시 자료구조로 저장하고 Cypher 질의어로 관계를 탐색한다. 이 위에 6장에서 소개한 GraphRAG — LLM으로 지식그래프를 구축하고, 그래프 탐색과 커뮤니티 요약으로 검색을 증강하는 기법(Edge et al., 2024) — 를 얹으면, 벡터 RAG가 놓치는 두 능력이 열린다. 여러 문서와 레코드를 가로지르는 다중 홉 질의("이 불량 로트에 들어간 자재의 공급업체가 납품한 다른 로트는?")와, 데이터 전체를 조망하는 전역 요약("올해 우리 품질 문제의 구조적 패턴은?")이다. Neo4j는 Microsoft GraphRAG 방식의 구현체와 하이브리드(벡터+전문+그래프) 검색을 공식 지원한다(Neo4j 공식 블로그).

오픈브레인 아키텍처에서 이 그래프는 단순한 검색 인덱스가 아니라 개인지식DB와 기업지식DB가 만나는 심장이다. 베테랑의 옵시디언 노트 — 수리 노하우, 거래처 메모, 30년의 암묵지 — 를 LLM이 구조화 추출하여 본인 승인 후 익명화를 거쳐 온톨로지에 기여하고(개인→기업), 회사의 사례·통계가 개인 질의의 컨텍스트로 제공되어 '내 경험 + 회사 이력'의 융합 답변이 돌아온다(기업→개인). 개인 노트는 온디바이스 원칙으로 보호되며, 5축 고장코드 같은 공통 코드체계가 두 세계의 연결 고리가 된다(오픈브레인, 2026). 2장에서 정립한 3뇌 구조가 기술 스택으로 착지하는 지점이 바로 여기다.

## 15.6 하이브리드 보안 모델: 공동 계층과 격리 계층, 그리고 데이터 주권

이 스택을 초소형 기업까지 확장한 것이 관리형 클라우드 모델인 OpenBrain Cloud다. 그 설계 철학은 "1인이 운영하는 시스템이 아니라, 1인을 운영해 주는 시스템"으로 요약된다(오픈브레인, 2026). 서버를 모르는 사장님을 위해 운영·보안·백업·업데이트를 관리형 클라우드가 통째로 떠안되, 데이터 민감도로 경계를 긋는 하이브리드 보안 모델을 취한다.

| 구분 | 관리형 공동 계층 | 고객 격리 계층 |
|---|---|---|
| 내용 | 자체 LLM 추론(GPU 공유), 공통 지식(상품분류·택배·세무 상식), 자동화 엔진(n8n), 보안·백업·업데이트 | 매출·정산 데이터, 고객 개인정보, 거래처·원가, 사업자 고유 노트(전용 암호화 DB) |
| 원리 | 다수가 비용 분담 → 1인 기업도 자체 LLM 사용 | 분리·암호화 → 유출·혼입 차단 |

핵심 명제는 "내 데이터는 내 금고에, 무거운 AI는 공동 발전소에서"다. GPU를 공동 운영하므로 1인 사업자도 구독료로 자체 LLM을 쓸 수 있고, 자체 LLM이므로 민감 데이터가 외부 API로 나가지 않는다. 여기에 Passkey(생체 인증) 로그인, 종단간 암호화, 자동 스냅샷 백업과 랜섬웨어 격리 보관, 무중단 자동 패치가 결합되어 "보안을 잘하라"가 아니라 "신경 쓸 일이 없게" 만드는 것을 지향한다. 제안서는 보안 사고의 90%가 패치·설정·백업 문제에서 비롯되는 만큼 이 구조가 사고 원인을 구조적으로 제거한다고 주장한다(오픈브레인, 2026). 데이터 주권 관점에서 이 모델은 클라우드 편의와 온프레미스 통제 사이의 실용적 절충이며, 3장에서 논한 한국 중소기업의 인력 현실 — IT 전담 0~1명 — 에 대한 아키텍처 차원의 응답이다. 개인정보 보호 규제와 AI 관련 법제가 강화되는 흐름 속에서, 민감 데이터가 어느 국경과 어느 사업자의 서버를 거치는지 답할 수 있는 구조 자체가 앞으로 기업의 신뢰 자산이 될 것이다.

## 15.7 손끝의 서드브레인: 모바일·스마트글라스 시나리오

이 스택의 사용자 접점은 PC 화면이 아니라 폰과 스마트글라스다. 음성·사진·터치로 들어가 답으로 돌아오는 한 루프 — 제안서의 세 시나리오는 이 아키텍처가 현장에서 어떻게 체감되는지를 보여준다(오픈브레인, 2026).

> **사례: 1인 온라인 셀러의 하루** 07:30, 침대에서 모바일로 밤사이 주문 14건의 자동 수집 브리핑을 받는다. '이어폰 품절 임박, 발주 권장' 알림에 "50개 발주서"라고 한마디 하면 발주 초안이 생성된다. 10:00, 작업대에서는 글라스 시야에 주문 송장과 품목이 표시되어 양손은 포장에 집중한다. 바코드 불일치는 즉시 경고되어 오출고가 사라지고, "완료" 음성에 송장이 자동 발급된다. 15:00, 카페에서 CS 12건의 자동 분류·답변 초안을 검토한다. 배송 문의 7건은 송장이 자동 첨부되었고, 까다로운 2건만 직접 확인해 일괄 발송한다.

> **사례: 5인 미만 제조 사장님의 하루** 08:00 출근길, "오늘 뭐부터?"라는 음성 질문에 'OO정밀 브래킷 D-2, 알루미늄 재고 부족, 5번 품목 불량 2건'이라는 한 문장 브리핑이 돌아온다. 11:00 작업대의 글라스에는 도면 옆에 BOM·작업표준·과거 불량 포인트가 표시된다. 불량이 나면 사진 한 장 — LLM이 부위를 판독해 이력을 기록한다. 17:00, "정리해줘" 한마디에 완성 120개, 불량률 1.6%, 자재 입고, 내일 1순위까지 장부·재고·일정이 자동 정리된다.

> **사례: 1~2인 물류의 하루** 09:00 입고장, 글라스가 박스를 보면 품목·수량·보관 위치를 자동 인식하고 "A-03로" 음성 한마디로 입고가 끝난다. 11:00 피킹, 출고 80건의 최단 동선이 안내되고 선반 앞에 '이 칸 3개'가 표시되며 오피킹은 즉시 경고된다 — 초보도 첫날부터 베테랑처럼 움직인다. 16:00 이동 중, "출고 현황?" 질문에 76건 완료, 미출고 4건(2건 재고 부족), 지연 1건의 사유가 답으로 오고 셀러용 리포트가 자동 생성된다.

세 시나리오의 공통 구조에 주목할 필요가 있다. 인터페이스는 다르지만(모바일 브리핑, 글라스 증강, 음성 질의) 그 아래에서 작동하는 것은 동일한 스택 — Odoo의 기록, n8n의 자동화, Dify·자체 LLM의 지능, 그래프의 문맥 — 이다. 세그먼트별로 운영 앱만 갈아 끼우고 공통 AI·보안 계층은 재사용하므로, 한 시스템이 세 업종을 커버하고 1인에서 5인, 50인으로 무중단 확장된다(오픈브레인, 2026).

## 15.8 도입 로드맵과 2단계 확장

도입은 무겁지 않다. 제안서의 표준 로드맵은 3주다. 1주 차 온보딩(테넌트 개설, 자체 LLM·운영 앱 배치, 마켓·택배 연동), 2주 차 지식 적재(상품·FAQ·작업표준·거래처 지식베이스 구축과 자동화 설정), 3주 차 현장 적용(글라스·모바일 앱 시나리오 리허설과 미세 조정). 사장님의 몫은 Passkey 등록, 기준정보 확인, 그리고 노하우 제공뿐이다(오픈브레인, 2026). 비용은 자체 LLM·자동화·보안·백업을 포함한 규모별 월 구독제로, 소프트웨어 라이선스는 0원이다.

확장도 단계적이다. 센서 기반 예지보전이 필요해지는 시점에 UMH(United Manufacturing Hub) 같은 산업 IoT 스택을 2단계로 추가한다(오픈브레인, 2026). 처음부터 모든 것을 세우지 않고, 경영의 질문이 자라는 속도에 맞춰 부스터를 더하는 것 — 이것이 4장에서 논한 목표지향 설계의 아키텍처적 표현이다. 다만 정직하게 덧붙이면, 이 스택은 구성 요소가 다섯 개 이상인 만큼 통합·운영의 복잡성이 단일 상용 제품보다 높다. 관리형 서비스(구축 대행과 운영 위탁)를 전제하지 않는 자체 구축이라면, 각 도구의 버전 호환성과 장애 대응 체계를 감당할 최소한의 기술 역량 또는 파트너 계약이 필요하다는 점을 도입 판단에 반영해야 한다.

## 핵심 요약

- 원플랫폼+쓰리부스터는 Odoo CE 단일 플랫폼에 계획(frePPLe)·AX(n8n+Dify)·지식(Neo4j GraphRAG) 부스터를 얹는 아키텍처로, 라이선스 비용 없이 IT 전담 0~1명으로 운영 가능한 구성을 지향한다.
- frePPLe는 Odoo 공식 커넥터를 갖춘 오픈소스 APS로, 유한능력 스케줄링·수요예측·What-if 시뮬레이션을 더해 처방적 계획의 엔진이 된다.
- n8n은 자체 호스팅 워크플로 허브로서 ETL과 시스템 횡단 자동화를, Dify는 자가 호스팅 LLM 앱 플랫폼으로서 업무별 사내 AI 앱과 RAG를 담당한다.
- LLM은 이중화한다. 민감·일상 과업은 Ollama 기반 자체 소형 모델이, 고난도 과업은 Claude 등 프론티어 모델이 맡아 데이터 주권과 성능을 함께 잡는다.
- Neo4j GraphRAG 지식 계층은 개인지식DB와 기업지식DB가 공통 온톨로지 코드로 만나는 심장이며, 다중 홉 추론과 전역 요약으로 벡터 RAG의 한계를 넘는다.
- 하이브리드 보안 모델은 "내 데이터는 내 금고에, 무거운 AI는 공동 발전소에서"로 요약된다. 공동 계층이 비용을, 격리 계층이 보안을 해결한다.
- 모바일·스마트글라스 시나리오(1인 셀러, 5인 제조, 1~2인 물류)는 같은 스택 위에서 운영 앱만 바꿔 세 업종을 커버하며, 3주 로드맵과 월 구독제로 도입된다. 예지보전이 필요해지면 UMH를 2단계로 추가한다.
