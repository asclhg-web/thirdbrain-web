## 환경 제약에 따른 설계 결정 (착수 시점)

- [D-01][전역] **Docker 데몬 없음** — 이 빌드 환경에서는 컨테이너를 띄울 수 없다.
  결정: 코어를 저장소-추상화(SQLite demo ↔ PostgreSQL prod)로 설계하고,
  deploy/docker-compose.yml은 현장 배치용으로 작성만 한다(기동 검증은 현장 몫).
  후속: 현장 서버에서 runbook.md대로 기동 검증 필요.
- [D-02][M4] **TensorFlow·RLlib 미설치** — 용량·GPU 제약.
  결정: 계획서의 "단순한 것부터" 규율대로 평활→GBDT(scikit-learn)를 기본 구현,
  딥러닝은 선택적 임포트 훅(백엔드 교체 지점)으로 남긴다. RL은 재고 Twin 안의
  정책 탐색(교차 엔트로피 방식)으로 구현 — 계획서의 안전장치(시뮬레이터 밖 학습 금지,
  산출은 카드로만)는 동일하게 강제된다.
  후속: GPU 서버 확보 시 M4-2의 TF 시계열, M4-4의 RLlib 백엔드 교체 검토.
- [D-03][M4] **MLflow 대신 경량 모델 카드 레지스트리** — 데모 모드에서 서비스 의존을
  없애기 위해 카드 레지스트리를 파일+DB로 자체 구현(필수 항목 강제 동일).
  prod compose에는 MLflow 서비스 포함 — 어댑터로 연결하는 구조.
- [D-04][M5] **Neo4j demo 대체** — demo 모드는 SQLite 트리플 저장소+networkx로 동작,
  Cypher 내보내기(neo4j_export)로 prod 이관. 스키마·확신도 로직은 동일.
- [D-05][M6] **LLM demo 대체** — Ollama 없는 환경이므로 demo 모드는 결정적
  문장 조립기(템플릿+그래프 근거)로 동작. "창작이 아니라 조립"이라는 M6 원칙과
  일치하며, Ollama 백엔드는 어댑터(judge/assembler.py의 LLMBackend)로 접속.
- [D-06][M1] **실제 Odoo 없음** — demo 모드는 합성 Odoo 스키마(sqlite)를 원천으로
  CDC를 폴링 방식으로 재현. prod용 논리 복제 구성은 문서·SQL로 제공.
