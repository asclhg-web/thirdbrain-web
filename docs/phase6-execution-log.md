## P6-1: 과금 모듈 — 구독·청구·미납 잠금 (2026-09-12 01:3x)

- **billing.py**: 인스턴스당 구독 1행(trial/standard/pilot), 월 청구
  멱등 발행(trial 0원은 발행 없음), 상태 기계 active→past_due(납기
  14일 경과)→locked(추가 14일 — 총 4주 유예, crit 1회)→수납 시 자동
  복귀. 잠금은 데이터를 지우지 않는다 — 로그인만 막고 원장·백업·복제는
  계속(문서·화면에 명시).
- **웹앱**: 로그인 가드 — 잠금 시 비관리자 402("데이터는 안전하게 보존
  중"), 관리자는 들어와 수납·해제. /billing(admin) 화면 — 플랜 설정·
  이번 달 발행·수납 처리·잠금 해제·청구 이력.
- **CLI**: axp billing status/set-plan/issue/paid/unlock/check.
- **스케줄러**: 야간 billing_check 단계(구독 미설정이면 무동작).
- 수납은 사람이 확인·기록 — PG(결제 대행) 자동 출금은 A4 결제 수단
  확정 후 이 상태 기계를 재사용(계획서 명시 순서 준수).
- 테스트 5건(멱등·trial 무청구·상태 기계 전이·미구성 무동작·로그인
  가드 402→해제) — 100+5skip(SQLite)/105(PG) 전부 통과.
- 참고: PG 스위트 첫 실행 대량 실패는 컨테이너 재시작으로 PG가 내려간
  것(기지 현상) — 기동 후 전부 통과, 코드 결함 아님.

## P6-2: 체험 신청·발급 — 승인제 기본, 자동 발급 스위치 (2026-09-12 01:4x)

- **signup.py**: 신청 접수(회사명·이메일 검증, 시간당 10건 완충) →
  pending 기록 → 발급(issue)이 tenant.create를 호출해 테넌트 생성.
  승인제와 자동 발급이 같은 기록·같은 생성 경로를 지난다(감사 동일).
- **승인제 결정 존중**: AXP_AUTO_ISSUE=1을 명시로 켜기 전에는 접수만
  되고 발급은 관리자가 /signups 화면에서 한다(발급·반려 버튼).
  자동 모드에선 신청 즉시 발급되고 초기 계정이 화면에 1회 표시.
  자동 발급 실패는 대기로 남아 사람이 잇는다(warn 경보).
- 공개 /signup 폼: 허니팟 필드(봇은 조용히 성공 화면만, 기록 없음).
  이메일 발송은 SMTP 결선 전까지 수동 — 화면·관리 화면에 명시.
- 테스트 5건(검증·승인제 기본·허니팟·자동 스위치·관리자 발급/반려) —
  105+5skip(SQLite)/110(PG) 전부 통과.

  모듈·알고리즘을 고르고 KPI를 선정 → 대시보드에서 성과를 보고 →
  개선점 피드백 → KPI 조정/데이터 재축적의 무한 개선 루프. 7단계
  실행계획서에 반영.
- **projects.py 신설(M0-P)**: 5대 영역 카탈로그(영역→플랫폼 실물 모듈·
  알고리즘·KPI 후보 — 존재하는 구성요소만 기재), 프로젝트 정의 시 선택
  영역의 KPI 자동 등재(목표는 사람이 설정), 목표 설정·조정은 feedback
  이력으로 보존(루프의 조정 단계).
- **KPI 실측 엔진(정직 구분)**: 사실 테이블에서 계산 가능한 지표
  (WAPE·폐기율·계획준수율·정비 평균 소요·월 고장 건수·승격 규칙 수)만
  측정하고, 불가한 지표(결품 일수·예측 편향·리드타임·질문 활용)는 값을
  지어내지 않고 '측정 전 + 필요한 데이터'를 말한다. 측정치는 이력으로
  쌓여 차트의 원천이 된다.
- 테스트 5건(카탈로그 등재·검증·정직 pending·실측/판정/조정 루프·
  시계열 누적).
- **P7-I1 발견·해소**: 스위트가 116개로 커지자 PG 프로파일별 캐시 연결

  종료 시 해당 스키마 연결을 닫고 캐시에서 제거. 111+5skip/116 전부 통과,
  잔류 연결 1개 실측.

## P7-3: KPI 무한 개선 루프 — 에이전트·스케줄러 결선 (2026-09-12 02:4x)

- **kpi_agent(7호 에이전트)**: 활성 프로젝트의 목표 설정 KPI를 최신 실측과
  대조 — 미달이면 개선 제안 판단 카드(현재값·목표·근거 출처·우선 점검
  지렛대=그 영역의 선택 모듈)를 승인함으로. 같은 KPI의 대기 카드가 있으면
  중복 생성하지 않는다. 목표 미설정 KPI는 제안하지 않는다(사람의 결정 선행).
- **환류**: kpi_improve 카드 승인 시 improve 피드백이 이력에 기록되고,
  다음 야간 측정이 재판정 — 여전히 미달이면 새 카드, 달성이면 침묵.
- **스케줄러**: projects_measure 단계(에이전트 실행 전 자동 측정) 추가 —
  측정→제안→승인→기록→재측정의 루프가 야간 배치에 상시 결선됨.
- **E2E 실증(테스트)**: 준수율 70%·목표 90% → 카드 1건(근거 문구 포함) →
  중복 방지 → 승인 → 피드백 기록 → 실적 95% 후 재측정 '달성' → 카드 0건.
- 스키마 교정: 측정 테이블에 m_id(동일 초 다중 측정 순서 보장) — 측정치는
  재계산 가능한 파생값이라 구버전 테이블은 재생성(원장 아님, 손실 무해).
- 테스트 117+5skip(SQLite)/122(PG) 전부 통과.
